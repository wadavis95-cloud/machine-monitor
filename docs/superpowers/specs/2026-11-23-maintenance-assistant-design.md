# Maintenance Assistant: Design (Phase 1)

Date: 2026-11-23 · Status: approved by the user 2026-11-23

## Intent

The user is a controls technician. At their site, operators report problems. Support groups (maintenance, controls) decide on repairs and log work orders in an EAM system (enterprise asset management, i.e. the maintenance software). Senior staff order parts. Two things go wrong:

1. **Stockouts:** the need for a part only shows up at breakdown, so lines wait for parts.
2. **Generic PMs:** preventive maintenance isn't targeted at specific machines, so wear stays hidden until a line goes down for hours or days.

The assistant turns Machine-Monitor's sensor data and RUL estimates into maintenance decisions. It answers "which machines should we worry about for the upcoming PM?", and it **drafts** work orders and part requests for a person to approve, so parts get ordered before failure.

This is a learning and interview project. The user must be able to explain every layer, and demonstrating a mainstream framework (LangChain/LangGraph) is an explicit goal.

## Goals (Phase 1)
- Answer fleet-planning questions in natural language, grounded in tool results, with citations.
- Combine **RUL** with **parts on hand and lead time** to recommend early part orders.
- Draft work orders and part requests, and let a person approve or reject them in the UI.
- Run on a free local model (Ollama). No paid API.

## Non-goals (Phase 1)
- RAG over work-order comments (Phase 2). Alerts and notifications (Phase 3). An MCP server (later stretch goal).
- Real authentication, multiple users, streaming responses, chat memory across questions.

## Anti-goals (failure even if it "works")
- The agent submits or spends anything by itself. Drafts only; a person approves.
- It invents facts: engine numbers, WO IDs, part numbers or RULs that aren't in a tool result.
- Any real company data, names, part numbers or screenshots in the repo, which is public.
- The existing dashboard or `make check` breaks, or CI needs Ollama.

## Constraints
- A Mac with 24 GB of memory; Ollama isn't installed yet (no Homebrew, so use the official installer).
- Python 3.14, Flask app, `make check` and protected `main` with CI. All work lands through PRs.
- Changes stay small and readable; Codex implements, Claude reviews.

## Approaches considered
| | Approach | Trade-off |
|---|---|---|
| A | Hand-written tool loop in plain Python | Most transparent, but no framework experience to show |
| **B** | **LangChain + LangGraph** ✅ chosen | Matches the user's certification and job ads. LangGraph keeps the loop visible as an explicit graph. The cost is more dependencies and some hidden behaviour |
| C | MCP server exposing the tools | Very current, but the chat lives outside the dashboard. Planned as a later extension on top of B |

**Chosen: B, built as an explicit LangGraph `StateGraph`** (a model node and a tool node joined by a conditional edge), not a prebuilt one-line agent, so every step of the loop is visible in code.

## Design

### Fake EAM database (`data/eam.sqlite`, generated by a seed script)
A deterministic seed script (seed 0) builds an invented but realistic dataset shaped like the user's workflow. Generic names only.
- `machines`: one row per engine unit (100), with a fictional line/area, the **current cycle** (a fleet snapshot: each engine fixed partway through its life), and the split (train/val) carried from the predictions.
- `parts`: about 10 to 15 part types mapped to subsystems the sensors reflect (e.g. HPC, fan, LPT, seals), with `on_hand`, `lead_time_days`, `unit_cost`. *(Claude's call)* All engines are the same model (as in FD001), so they share one parts list (bill of materials). `parts_for` returns that list. Linking a symptom to a specific part comes from work-order history in Phase 2.
- `work_orders`: past corrective and PM orders with type, symptom, action taken, parts used, fictional technician initials, free-text `comments`, opened/closed dates, and `status` (`closed`, `open`, `draft`). The comments are written to reflect sensor symptoms so Phase 2 has real material to search.
- `part_requests`: `part_id`, `qty`, `reason`, `status` (`draft` → `submitted` / `rejected`), `created_by`.

**Snapshot without hindsight** *(Claude's call)*: the seed picks each engine's current cycle as a seeded 40–95% of its life. Knowing the true life is unavoidable when building a demo, like the truncated NASA test set. But tools only expose readings up to the current cycle and the **predicted** RUL, never `rul_true` or the final cycle. Eval answers are checked against those same tool outputs.

**Time:** 1 cycle = 1 day, so that "~20 days left vs a 30-day lead time" reads naturally.

**Caveat (documented, not fixed):** RUL estimates for engines in the training split are in-sample, so they're optimistic. Tool output includes `split` so the agent can say so.

### Warning flags move to Python
Today the yellow and red flags exist only in the dashboard's JavaScript. Port the rule to a small Python function (yellow: 3 high T24 readings in the last 10 cycles; red: 5 consecutive cycles outside the band) and test it against the same cases as `test_dashboard.js`. The dashboard JS stays as is. *(Claude's call)* Tools report the flag **at the current cycle** (computed over the last 10 cycles), not a sticky "was ever warned" state.

### Tools (plain functions with typed arguments and docstrings, wrapped as LangChain tools)
1. `fleet_status(top_n)`: engines ranked by risk (RUL ascending; flags break ties), each with RUL, flag level, current cycle, split.
2. `engine_detail(unit)`: RUL, flag level, recent T24 trend, open work orders.
3. `parts_for(unit)`: the relevant parts with on hand, lead time, and **order-by** status (needs ordering when `on_hand == 0` and `lead_time_days ≥ RUL − buffer`; buffer = 10 days).
4. `work_orders(unit, status)`: past and open work orders for a unit.
5. `draft_work_order(unit, summary, reason)` and `draft_part_request(part_id, qty, reason)`: insert rows with `status='draft'` and return the new ID. These are the only writes. *(Claude's call)* The safety gate is the human approval step, not guessing intent: a draft does nothing until approved. The app caps it at 3 drafts per question, and "drafts only when asked" is scored in the eval as model behaviour.

### Agent
- `ChatOllama` (model from an env var; default `qwen3:8b`, temperature 0) with the tools bound, in a LangGraph `StateGraph`: `model → tools → model …` until there are no tool calls, capped at 6 tool calls.
- The system prompt says: use only tool results; cite them inline (`[fleet_status]`, `[WO-123]`); never say anything was ordered or submitted, only drafted; say plainly when data is missing.
- Each model call and tool call writes one key=value log line (name, duration_ms, outcome), matching the existing request logs.

### API and UI
- `POST /api/assistant {question}` → `{answer, tool_calls: [{name, args}], drafts: [ids]}`. Synchronous, no streaming.
- `GET /api/drafts`, `POST /api/drafts/<id>/approve|reject`. *(Claude's call)* Lifecycles: a work order goes `draft → open` (approve) or `draft → rejected`; a part request goes `draft → submitted` or `draft → rejected`. Nothing real happens.
- A new `/assistant` page: a question box, the answer, a collapsible "How I got this" list of tool calls, and a drafts list with Approve/Reject buttons. The existing dashboard is untouched apart from a link.

### Watching the graph run (user requirement)
The user wants to **see LangGraph executing on screen**, not have it summarised in the terminal. The builder provides:
- On `/assistant`, a drawing of the graph (`graph.get_graph().draw_mermaid()`), with each step (model call or tool call, its arguments, a short result and duration) appearing as it happens.
- The official visual debugger, **LangGraph Studio** (`langgraph dev`), set up as an optional `make studio` target. Check its current setup requirements (account, network) before relying on it, and note them in the README.

### Evaluation (`eval-first`)
A golden set of about 15 questions with checkable facts (e.g. "top 3 at-risk engines" must match `fleet_status`; "what should we order" must match the order-by rule). Scored on right tools called, facts correct, no invented IDs, and drafts only when asked. Run it with `make eval` locally against Ollama; it's not part of CI. The baseline score is recorded in `reports/`.

### Testing and CI
- Unit tests for the seed script (deterministic), flag rule, tools and draft endpoints. These are pure Python with a temporary SQLite file.
- The agent graph is tested with a scripted fake chat model that emits fixed tool calls, so CI never needs Ollama.
- New dependencies (langchain-core, langgraph, langchain-ollama) are pinned in `requirements.txt`.

## Later phases (not designed here)
- **Phase 2:** RAG over work-order comments (local embeddings via Ollama) to answer "what fixed this last time?" and to give non-technical users step-by-step troubleshooting.
- **Phase 3:** alerts. A scheduled rule detects risk; the LLM only writes the explanation.
- **Stretch:** an MCP server exposing the same tools.
- **Possible:** replace polling on `/assistant` with Server-Sent Events (SSE), so the server pushes each step instead of the page asking for it. Phase 1 uses polling (decided 2026-11-23, see the plan) because the dashboard already uses that pattern.

## Left to the builder
The exact seed values and comment templates, the prompt wording, page styling, table column details beyond those listed, and the choice of a different 8B model if `qwen3:8b` handles tools poorly (record the reason in `experiments.md`).
